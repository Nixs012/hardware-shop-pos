# Hardware Shop POS — Project Folder Structure Blueprint
### Stack: Flutter (Android billing app) + Firebase (backend) + Next.js (web back-office)

Use this as the target structure when prompting Antigravity to scaffold each piece. It's a monorepo — one root folder, two apps inside, sharing a common data model conceptually (not literally shared code, since Flutter/Dart and Next.js/TypeScript can't share source files directly).

---

## Root layout

```
hardware-shop-pos/
├── .agents/
│   └── skills/
│       ├── pos-domain-rules/
│       │   └── SKILL.md
│       ├── escpos-printing/
│       │   └── SKILL.md
│       └── report-generation/
│           └── SKILL.md
├── app/                        ← Flutter Android billing app
├── web/                        ← Next.js back-office dashboard
├── firebase/                   ← Firestore rules, indexes, cloud functions (if any)
├── docs/                       ← project docs, client requirements, receipts template, etc.
├── .gitignore
└── README.md
```

Keep the requirements questionnaire and the development plan doc we made earlier inside `docs/` so they're version-controlled alongside the code, not lost in email threads.

## `/app` — Flutter billing app

```
app/
├── lib/
│   ├── main.dart
│   ├── models/
│   │   ├── product.dart          # id, name, sku, category, cost_price, selling_price, quantity_on_hand, low_stock_threshold, unit
│   │   ├── sale.dart              # id (client UUID), timestamp, staff_id, payment_method, line_items[]
│   │   ├── sale_line_item.dart    # product_id, quantity, unit_price_at_sale, unit_cost_at_sale
│   │   ├── staff.dart             # id, name, role (admin/cashier), pin or auth uid
│   │   └── expense.dart           # id, date, category, amount, note
│   ├── services/
│   │   ├── firestore_service.dart # all reads/writes to Firestore
│   │   ├── sync_service.dart      # offline queue + conflict resolution (see pos-domain-rules skill)
│   │   ├── printer_service.dart   # ESC/POS connection + print logic (see escpos-printing skill)
│   │   └── auth_service.dart      # staff login / role check
│   ├── screens/
│   │   ├── billing/               # main checkout/till screen
│   │   ├── products/              # add/edit stock
│   │   ├── reports/                # daily/weekly/monthly, stock balance, profit-loss
│   │   ├── settings/               # printer pairing, shop details, staff management
│   │   └── auth/                   # login screen
│   ├── widgets/                    # shared UI components (receipt preview, product card, etc.)
│   └── utils/
│       ├── currency_formatter.dart
│       └── date_range_helper.dart  # shared daily/weekly/monthly range logic
├── android/                        # standard Flutter Android platform folder
├── test/                           # widget + unit tests
├── pubspec.yaml
└── firebase_options.dart           # generated by flutterfire configure
```

**Key packages to add in `pubspec.yaml`:** `cloud_firestore`, `firebase_auth`, `firebase_core`, `esc_pos_bluetooth`, `esc_pos_utils`, `connectivity_plus` (for detecting online/offline state), `sqflite` or `hive` (local offline cache before sync).

## `/web` — Next.js back-office dashboard

```
web/
├── src/
│   ├── app/                        # Next.js App Router
│   │   ├── dashboard/
│   │   ├── products/               # bulk import/export, edit catalog
│   │   ├── reports/
│   │   │   ├── daily/
│   │   │   ├── weekly/
│   │   │   ├── monthly/
│   │   │   └── profit-loss/
│   │   ├── staff/                  # manage cashier accounts + roles
│   │   └── login/
│   ├── lib/
│   │   ├── firebase.ts             # Firebase client config/init
│   │   ├── firestore-queries.ts    # shared query builders (see report-generation skill)
│   │   └── auth.ts
│   ├── components/
│   │   ├── ReportTable.tsx
│   │   ├── StockTable.tsx
│   │   └── ExportButton.tsx        # CSV/PDF export
│   └── types/
│       └── index.ts                # shared TypeScript interfaces mirroring the Flutter models
├── public/
├── package.json
└── next.config.js
```

**Key packages:** `firebase` (client SDK), `papaparse` or `xlsx` (Excel import/export), `recharts` or `chart.js` (trend charts for weekly/monthly views), `jspdf` or similar (PDF export).

## `/firebase` — backend config

```
firebase/
├── firestore.rules      # security rules — THIS is where staff role permissions are actually enforced (see pos-domain-rules skill, section 4)
├── firestore.indexes.json
├── functions/            # optional: Cloud Functions for scheduled report pre-aggregation (see report-generation skill, section 3)
│   ├── index.js
│   └── package.json
└── firebase.json
```

**Firestore collections (top-level):**
```
/products/{productId}
/sales/{saleId}
/staff/{staffId}
/expenses/{expenseId}
/daily_summaries/{date}     ← pre-aggregated, per report-generation skill
```

## Suggested prompts to give Antigravity, in order

1. *"Create a new Flutter project inside /app targeting Android, with Firebase already added as a dependency."*
2. *"Set up Firebase in this project — Firestore, Auth, and generate firebase_options.dart for the Flutter app."*
3. *"Create the Product, Sale, SaleLineItem, Staff, and Expense models in /app/lib/models per the pos-domain-rules skill."*
4. *"Create a new Next.js app inside /web with TypeScript and Tailwind, connected to the same Firebase project."*
5. *"Write firestore.rules enforcing the admin/cashier permission split from the pos-domain-rules skill."*

Starting in this order means the data model and security rules exist before either UI is built — much easier to get right early than to retrofit later.
